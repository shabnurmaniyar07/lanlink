# LanLink wire protocol — v1

Frozen from the implementation in `src/lanlink/` at application version `0.1.0`.
Everything here is verified by `tests/test_protocol_contract.py`; nothing is aspirational.

This protocol is **internal transport between paired devices**. It is not a public web API and it
never serves a user interface. Every LanLink client is a native application.

Companion files:

- `openapi.yaml` — generated from the running app by `tools/export_openapi.py`. Paths, methods,
  parameters and request bodies. Regenerate it whenever `api.py` changes.
- `schema.json` — JSON Schema for every response body, which OpenAPI cannot describe here because
  the handlers are declared as plain dicts.
- `../../tools/conformance.py` — a black-box checker. Point it at a live node and it verifies the
  behaviour described below over a real pinned TLS connection. Use it to prove a new client's
  server side is correct:

  ```
  python tools/conformance.py --host 192.168.1.20 --port 8765 --code 48210937
  ```

---

## 1. Protocol version

| | |
|---|---|
| Protocol family | `v1` |
| Advertised as | mDNS TXT `api=v1` |
| URL prefix | `/v1` |
| Application version | separate, reported as `device.version` |

A client MUST check `api` from the mDNS TXT record (or `GET /health` when connecting by address)
before speaking. An unknown value means *do not attempt the exchange*.

Compatibility rules for the lifetime of v1:

- Endpoint paths, methods, request parameters and response field **names and types** do not change.
- New optional response fields MAY be added. Clients MUST ignore members they do not recognise.
- New endpoints MAY be added under `/v1`.
- Removing a field, changing its type, or changing a status code requires `/v2`.

## 2. Device identity

Identity is the **certificate**, not the address and not the name.

| Field | Meaning |
|---|---|
| `id` | UUID4 generated on first run, stored in settings. Survives rename, certificate renewal, and address change. |
| `name` | Owner-chosen display name. Not unique, not authenticated, never used for authorisation. |
| `hostname` | OS hostname, informational. |
| `platform` | `platform.system()` — `Windows`, `Linux`, `Darwin`. A native Android client reports `Android`. |
| `version` | LanLink application version. |
| `fingerprint` | SHA-256 of the device certificate in DER form, lowercase hex, 64 characters. Empty only when the owner has switched TLS off. |

The device object is public: it contains no token, no key and no filesystem path.

## 3. mDNS discovery

| | |
|---|---|
| Service type | `_lanlink._tcp.local.` |
| Instance name | `<device name>._lanlink._tcp.local.` |
| Server | `lanlink-<first 8 of device id>.local.` |
| Port | the TCP port the node listens on, default `8765`, `8765`–`8774` when busy |
| Addresses | IPv4 only; the first A record is used |

TXT records (all UTF-8 strings, all present):

| Key | Value |
|---|---|
| `id` | device id — the only mandatory field. A record without a non-empty `id` MUST be ignored. |
| `name` | display name |
| `api` | `v1` |
| `platform` | `Windows`, `Linux`, `Darwin`, `Android` |
| `version` | application version |
| `scheme` | `https`, or `http` when the owner disabled TLS |
| `fp` | **first 32 hex characters** of the certificate fingerprint |

`fp` is a **hint for matching a known device, not a pin**. Pin the full 64-character fingerprint
taken from an invite or from the certificate the peer presents, confirmed by the owner (§4).

Discovery is a convenience. **Being discovered grants nothing.** A device that has never paired
cannot read a single byte.

Manual entry is always available: `host:port`, or a `lanlink://pair` invite (§5).

## 4. TLS requirements

- Transport is **HTTPS**. `http` exists only as an owner-selected troubleshooting mode and a client
  SHOULD warn when it sees `scheme=http`.
- Each device generates its own certificate on first run: **P-256 ECDSA, self-signed, SHA-256,
  valid 3650 days**, regenerated automatically inside the last 30. A regenerated certificate is a
  new pin — peers must re-pair, which is the intended, visible outcome.
  - Subject / Issuer: `CN=lanlink-<id[:8]>, O=LanLink, OU=<full device id>`
  - SAN: `DNS:lanlink-<id[:8]>.local`, every LAN IP address at generation time, and the sanitised
    device name.
- There is **no certificate authority**. Do not attempt CA validation and do not expect it to pass.
- **Hostname verification is off by default.** LAN addresses change; the pinned certificate is the
  identity. A client MAY verify the SAN as a secondary check but MUST NOT treat a SAN mismatch on a
  correctly pinned certificate as a failure.
- Minimum version **TLS 1.2**.

### Pinning

1. Before pairing, fetch the peer's certificate (`fetch_peer_certificate`, or take it from the
   invite's `fp`).
2. Show the owner the **short fingerprint** — the first 16 hex characters, uppercase, in groups of
   four, e.g. `A1B2 C3D4 E5F6 0789` — and have them compare it with the other device's screen.
3. Store the certificate PEM with the pairing.
4. Every later connection trusts **exactly that certificate and nothing else**
   (`ssl.create_default_context(cadata=peer_pem)`, `check_hostname = False`).
5. If the presented certificate no longer matches the pin, **refuse the connection**. Do not offer
   "continue anyway". A changed certificate means either a reinstall — in which case re-pair
   deliberately — or an impersonation attempt.

Android note: a `javax.net.ssl.X509TrustManager` holding a single trusted certificate, plus a
`HostnameVerifier` that accepts the pinned peer. `Network Security Config` domain pinning is not
usable here because the pin is per-device and learned at runtime.

## 5. Pairing

Pairing is the only way a device gains access. It is deliberately awkward.

### The rules

| Rule | Value |
|---|---|
| Pairing mode | **off by default**; no code exists until the owner switches it on |
| Code | **8-digit** decimal, cryptographically random |
| Lifetime | **120** seconds |
| Uses | one — a success switches pairing mode off |
| Rate limit | token bucket per source address: burst 5, refill 1 per second |
| Lockout | **five** wrong codes switch pairing mode off entirely |
| Approval | the owner may additionally be asked to approve the named device |
| Comparison | constant-time |

The code is never transmitted by LanLink. The owner reads it off one screen and types it into the
other, or scans the QR.

### Invite URL

```
lanlink://pair?host=192.168.1.20&port=8765&code=12345678&id=<device id>&name=Workshop%20PC&fp=<64 hex>&scheme=https
```

Every parameter except `host` and `port` is optional. `fp` carries the **full** fingerprint so the
receiving device pins the right identity rather than trusting whatever answers on that address.
The same string is what the QR code encodes. A bare `host:port` typed by hand is also accepted;
the port defaults to `8765`.

### The exchange

```http
POST /v1/pair
Content-Type: application/json

{"client_id": "b2f1c0de-...", "client_name": "Pixel 8", "pair_code": "48210937"}
```

| Field | Rule |
|---|---|
| `client_id` | 8–128 characters. Stable per installation — a UUID4 generated once and kept. |
| `client_name` | 1–80 characters. Shown to the owner during approval. |
| `pair_code` | 6–20 characters, digits only. The current implementation always issues 8. |

Success — **200**:

```json
{"token": "rrGziGDKKqdrdazAQMjKp20MM8eYFH_m4iBPyMTk2wg",
 "device": {"id": "...", "name": "Workshop PC", "hostname": "WORKSHOP",
            "platform": "Windows", "version": "0.1.0", "fingerprint": "a1b2...64 hex"}}
```

Failure:

| Outcome | Status | Meaning for the user |
|---|---|---|
| `not_armed` | **409** | The other device is not in pairing mode, or the code expired. |
| `invalid_code` | **403** | Wrong code. |
| `declined` | **403** | The owner refused the request. |
| `rate_limited` | **429** | Too many attempts too quickly. Wait and retry. |
| `locked_out` | **429** | Five wrong codes; pairing mode was switched off over there. |

**Retry behaviour.** `409 not_armed` is the normal case when the person starts on the wrong device.
A client MAY keep the request pending and re-attempt on an interval (the desktop uses 120 s at a
1 s interval) so the two people do not have to synchronise. It MUST NOT retry `403` or `429`, and
MUST stop the moment the user cancels. **Never pair automatically because a device was
discovered.** The code and, where configured, the owner's approval are always required.

## 6. Authentication

Every endpoint except `GET /health`, `GET /v1/device` and `POST /v1/pair` requires:

```
X-LanLink-Token: <token>
```

| | |
|---|---|
| Format | `secrets.token_urlsafe(32)` — 43 URL-safe base64 characters from 32 random bytes |
| Storage on the server | **SHA-256 hash only**; the token itself is never written down |
| Comparison | constant-time, across all paired devices |
| Maximum accepted length | 512 characters |
| Expiry | none — a token is valid until revoked |
| Transport | the header, over TLS. Never a query parameter, never a cookie. |

A missing, unknown or malformed token is **401** with a `detail` sentence.

**Client storage.** Treat the token as a password. On Android use `EncryptedSharedPreferences` or a
Keystore-wrapped key; the Windows desktop seals it with DPAPI. Losing it means re-pairing, which is
cheap — never trade storage security for convenience.

**Lifecycle.** Issued at pairing; revoked by `DELETE /v1/pairings/{client_id}` (self only) or by the
owner locally. After revocation every request returns 401 immediately.

## 7. Device model

```http
GET /v1/device
```

```json
{"device": {"id": "...", "name": "Workshop PC", "hostname": "WORKSHOP",
            "platform": "Windows", "version": "0.1.0", "fingerprint": "a1b2..."},
 "pairing_armed": false}
```

Unauthenticated on purpose: a client uses it to show "that device exists and is reachable", and to
poll `pairing_armed` while waiting for the owner to switch pairing on.

```http
GET /health
```

```json
{"status": "ok", "device": { ... }}
```

Use `/health` for reachability probing. It is cheap and does not touch the filesystem.

## 8. Shared-folder model

```http
GET /v1/shares
X-LanLink-Token: ...
```

```json
{"shares": [{"id": "share_7e7a4e8a2bff", "name": "Demo", "permissions": "rw", "available": true}]}
```

| Field | Meaning |
|---|---|
| `id` | `share_` + 12 hex characters. Stable for the life of the share. |
| `name` | Display name. **The real filesystem path is never sent.** |
| `permissions` | Subset of `r`, `w`, `d` in that order |
| `available` | `false` when the folder is missing right now (unplugged drive, deleted folder). The share stays configured; file operations on it then fail with 404 `This shared folder is currently unavailable.` |

| Flag | Grants | Denied with |
|---|---|---|
| `r` | list, download, checksum, properties, partial status | — see below |
| `w` | upload (`POST /v1/uploads`, `PUT /v1/files`), finalize, create folder, rename, and being the **destination** of a copy or move | 403 `This shared folder is read-only.` |
| `d` | delete, and being the **source** of a move | 403 `Deleting is not permitted in this shared folder.` |

Defaults are `rw`. Delete is opt-in because it is the irreversible one.

**Read is implicit.** Setting permissions normalises the string to the known flags and always
re-adds `r`, so a share that is shared at all is readable and the observable sets are `r`, `rw`,
`rd`, `rwd`. Read endpoints therefore carry no permission gate. A client should still not assume a
future peer behaves that way: handle a 403 from a read endpoint gracefully rather than treating it
as impossible.

A client MUST render the permission set — greying out actions the share does not allow is better
than letting the user discover it through a 403.

Only folders the owner explicitly added are reachable. **Whole disks are never exposed and there is
no endpoint that enumerates the filesystem.**

## 9. Folder listing

```http
GET /v1/shares/{share_id}/list?path=cad/parts
```

```json
{"entries": [
  {"name": "Assemblies", "path": "cad/parts/Assemblies", "kind": "folder", "size": null,
   "modified_at": 1755000000.0},
  {"name": "gripper.step", "path": "cad/parts/gripper.step", "kind": "file", "size": 4823910,
   "modified_at": 1755100000.5}
]}
```

- `path` is optional; omitted or `""` lists the share root.
- Returned `path` values are **share-relative, POSIX separators, no leading slash** — send them back
  verbatim as the next `?path=`.
- `size` is `null` for folders.
- `modified_at` is **Unix epoch seconds as a JSON number**, fractional.
- Sorted folders first, then case-insensitive by name.
- Entries ending in `.lanlink-part` are **never listed**: an unfinished upload is not yet a file.
- Unreadable entries are skipped rather than failing the whole listing.

There is no recursion parameter. Walk it a folder at a time (§20).

## 10. File metadata

```http
GET /v1/shares/{share_id}/properties?path=a.txt
```

```json
{"name": "a.txt", "path": "a.txt", "kind": "file", "size": 5,
 "modified_at": 1755000000.0, "created_at": 1755000000.0, "accessed_at": 1755000001.0,
 "extension": ".txt", "read_only": false, "share": "Demo", "share_permissions": "rw"}
```

`path=""` describes the share root; `name` is then the share's display name and `path` is `""`.
Folders additionally carry `item_count`:

```json
"item_count": {"folders": 1, "files": 12}
```

`created_at` is `st_ctime` — creation time on Windows, inode-change time on POSIX. `read_only` is
filesystem writability on the serving device, which is **separate from** `share_permissions`; an
action needs both.

```http
GET /v1/shares/{share_id}/checksum?path=a.txt
```

```json
{"sha256": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824", "path": "a.txt"}
```

Computed on demand by reading the whole file. Allow a generous read timeout (the desktop uses
600 s) and do not call it on a metered connection for a large file you are not about to transfer.

## 11. Download

```http
GET /v1/files/{share_id}?path=cad/parts/gripper.step
X-LanLink-Token: ...
```

**200**, body is the file. Headers:

```
Accept-Ranges: bytes
Content-Length: 4823910
Content-Disposition: attachment; filename="gripper.step"
Content-Type: <guessed from the extension, often application/octet-stream>
Last-Modified, ETag
```

### Resuming

```http
Range: bytes=1048576-
```

**206** with:

```
Content-Range: bytes 1048576-4823909/4823910
Content-Length: 3775334
Accept-Ranges: bytes
Content-Disposition: attachment; filename="gripper.step"
Content-Type: application/octet-stream
```

Exactly two forms are served, and the reply is never a multipart body:

| `Range` | Result |
|---|---|
| `bytes=N-` where `N < size` | **206**, `N` to the end |
| `bytes=N-M` where `N < size` | **206**, `N` to `min(M, size-1)` inclusive |
| `bytes=N-` where `N >= size` | **416**, `Content-Range: bytes */<size>` |
| suffix (`bytes=-500`) | **200**, whole file |
| multi-range (`bytes=0-9,20-29`) | **200**, whole file |
| another unit (`items=5-`), or malformed | **200**, whole file |
| `M < N` | **200**, whole file |

The unit is case-insensitive (`BYTES=99-` works).

> A resuming client MUST check the status code. **200 in reply to a `Range` request means start
> over** — truncate whatever was already written. Appending to it would silently corrupt the file.
> This is exactly what `download_runner` does. Always honour the returned `Content-Range` rather
> than assuming the request was satisfied as written.

Folders cannot be downloaded; `path` must name a file (§20).

## 12. Upload

Two ways in. **Prefer the streaming one for anything that is not tiny.**

### 12a. Streaming, resumable — `PUT /v1/files/{share_id}`

```http
PUT /v1/files/{share_id}?path=Incoming&name=photo.jpg&offset=0&finalize=true&sha256=<64 hex>
Content-Type: application/octet-stream

<raw bytes>
```

| Parameter | Default | Meaning |
|---|---|---|
| `path` | `""` | Destination **folder**, share-relative. Must already exist. |
| `name` | required | Destination **file name**, one safe leaf (§29). |
| `offset` | `0` | Byte offset these bytes start at. |
| `finalize` | `true` | Publish under the real name when the body ends. |
| `sha256` | — | Verified before publishing. |

Bytes accumulate in a `<name>.lanlink-part` sidecar. The file only appears under its real name once
the transfer completes and, when supplied, matches its checksum — so **an interrupted upload can
never be mistaken for a finished one**.

```json
{"path": "photo.jpg", "received": 4194304, "complete": false}
```

```json
{"path": "photo.jpg", "bytes": 8388608, "received": 8388608, "complete": true}
```

Offset rules:

- `offset > bytes held` → **409** with header `X-LanLink-Received: <held>`; resume from there.
- `offset < bytes held` → the sidecar is truncated to `offset` and writing continues, so the bytes
  always line up.
- The finished file already exists → **409** `A file with this name already exists.`
  **Uploads never overwrite.**
- Body exceeds the owner's upload limit → **413**, and the sidecar is discarded.
- Checksum mismatch at finalize → **409**, and the sidecar is discarded.

A dropped connection **keeps** the sidecar. That is the point: query §12c and continue.

### 12b. Multipart, single shot — `POST /v1/uploads/{share_id}`

```http
POST /v1/uploads/{share_id}?path=Incoming
Content-Type: multipart/form-data; boundary=...

file=@photo.jpg
```

```json
{"path": "photo.jpg", "bytes": 8388608}
```

No resume, no checksum. A failure discards the partial file so the retry is not blocked. Suitable
for small files and simple clients; not for a phone on a flaky connection.

### 12c. Resume state — `GET /v1/shares/{share_id}/partial`

```http
GET /v1/shares/{share_id}/partial?path=Incoming&name=photo.jpg
```

```json
{"received": 4194304, "complete": false, "size": null}
```

`complete: true` with a `size` means the finished file is already there and a new upload under that
name will be refused with 409.

### 12d. Finalize separately — `POST /v1/shares/{share_id}/finalize`

```http
POST /v1/shares/{share_id}/finalize?path=Incoming&name=photo.jpg&sha256=<64 hex>
```

```json
{"path": "photo.jpg", "bytes": 8388608, "complete": true}
```

For when the body was sent with `finalize=false`. **409** if there is no sidecar, if the real name
is taken, or if the checksum does not match — the sidecar is discarded in the last case.

## 13. Create folder

```http
POST /v1/shares/{share_id}/folders
{"path": "cad", "name": "New Parts"}
```

```json
{"result": "ok", "name": "New Parts"}
```

Requires `w`. `path` is the parent folder, `name` is one safe leaf (§29). **409** if the parent is
missing, the name already exists, or the name is not acceptable. Not recursive: create one level at
a time.

## 14. Rename

```http
POST /v1/shares/{share_id}/rename
{"path": "cad/old.step", "new_name": "new.step"}
```

```json
{"result": "ok", "name": "new.step"}
```

Requires `w`. Renames a file **or** a folder in place; it cannot move an item between folders — use
§17/§18 for that. The share root itself cannot be renamed. **409** if the target exists, if the new
name equals the old one, or if the item is gone.

---

## 15. Delete

```http
DELETE /v1/shares/{share_id}/entries?path=cad/old.step&recursive=false
```

```json
{"result": "ok", "kind": "file"}
```

Requires `d`. `kind` is `file` or `folder`. A non-empty folder needs `recursive=true`; without it,
**409** `This folder is not empty. Confirm a recursive delete first.` — surface that as a
confirmation, not as an error. The share root itself cannot be deleted remotely.

## 17. Copy

```http
POST /v1/operations
{"source_share_id": "share_a", "source_path": "a.txt",
 "destination_share_id": "share_b", "destination_path": "Incoming",
 "operation": "copy"}
```

```json
{"result": "ok", "path": "Incoming/a.txt"}
```

Both shares are on **the device being asked**. This is a server-side copy between two of its own
shares; the bytes never cross the network. Requires `w` on the destination.

`path` is **share-relative to the destination share**. It is never an absolute filesystem path.

**409** if the destination already has that name, if source and destination are the same file, or
if the source is missing. Files only — a folder is not a valid source.

---

## 18. Move

The same endpoint with `"operation": "move"`. Requires `w` on the destination **and** `d` on the
source.

The implementation copies, verifies the size, and only then unlinks the source. **A move never
deletes first.** If verification fails the destination is removed and the source is left untouched.

---

## 19. Remote-to-remote relay

There is **no relay endpoint**. Moving a file between two *other* devices is a client-side
composition, not a server feature:

1. `GET /v1/files/{share}` on device A, streaming.
2. Feed those bytes straight into `PUT /v1/files/{share}` on device B.
3. Only after B confirms the byte count, `DELETE` on A — and only for a move.

The orchestrating device never writes the file to its own disk. See `relay_runner` in
`transfers.py` for the reference implementation, including resume: query B's partial state first,
then `Range`-request A from that offset.

Checksum handling: ask A for `sha256` first and pass it to B as the `sha256` parameter, so B
verifies end to end. If A does not answer the checksum request, continue without it rather than
failing the transfer.

---

## 20. Recursive folder transfer

Also a client-side composition. There is no folder download and no archive endpoint.

1. Walk with `GET .../list`, breadth-first, collecting sub-folder paths and file entries. Paths are
   share-relative so they replay verbatim against another node.
2. Recreate the tree on the destination with `POST .../folders`, **parents before children** — a
   single call creates one level only. `409 already exists` while recreating a tree is success, not
   an error.
3. Transfer files one at a time (§11/§12), preserving each file's path relative to the folder root.

Empty folders are preserved by step 2. A file that fails should not abort the rest; report it and
continue.

---

## 21. Transfer progress

Progress is a **client-side** concept. The protocol carries no job ids and no progress endpoint.

- Total: `Content-Length` on download; the local file size on upload.
- Done: bytes read from or written to the socket.
- On resume the starting point is the `Range` offset (download) or `received` (upload) — count those
  as already transferred so the bar does not restart.

Chunk size in both reference implementations is **512 KiB**.

---

## 22. Cancel

Close the connection. There is nothing to tell the server.

- **Download** — the client's `.lanlink-part` sidecar is kept, so the retry resumes.
- **Streaming upload** — the server keeps its sidecar for the same reason. It is not visible in
  listings.
- **Multipart upload** — the partial file is discarded so the retry is not blocked by a 409.
- **Move** — the source is untouched, because deletion only happens after verification.

Cancelling is always safe: no operation leaves a half-written file under a real name.

## 23. Retry

| Failure | Retry? |
|---|---|
| Connection dropped, timeout, 5xx | Yes — resume from the offset (§11, §12c). |
| **409** on `PUT` with `X-LanLink-Received` | Yes — immediately, at that offset. |
| **409** already exists | No — ask the user for a different name. |
| **401** | No — the pairing was revoked. Pair again. |
| **403** | No — permissions will not change by asking twice. |
| **404** | No — it is gone, or the path is not allowed. |
| **413** | No — the file exceeds the owner's limit. |
| **416** | Restart the transfer from zero; the file changed underneath. |
| **429** during pairing | Yes, after a wait — but never for `locked_out`. |

Back off between attempts. A stale pinned certificate never resolves by retrying.

---

## 24. SHA-256 verification

- Lowercase hex, 64 characters, of the whole file.
- **Download**: fetch `.../checksum` first, verify the completed `.lanlink-part`, and only then
  rename it into place. A file that fails is discarded, never published under its real name.
- **Upload**: pass `sha256` to `PUT` or to `finalize`. The receiver verifies before publishing.
- **Relay**: A's checksum is passed to B, so the check is end to end.
- A peer that cannot answer the checksum request is not a failure — transfer without it rather than
  refusing.

Verification is always on in the desktop client and is not a user-facing setting.

## 25. Partial-file handling

| | |
|---|---|
| Suffix | `.lanlink-part` |
| Location | beside the destination, in the same folder |
| Naming | `<real name>.lanlink-part` |
| Listed? | **Never** |
| Published | atomically, by rename, only after size and checksum agree |

Both ends use the same convention. A client MUST NOT create a file with this suffix for any other
purpose, and MUST NOT present one to the user as a real file.

## 26. Error codes

Every 4xx except 422 is:

```json
{"detail": "A file with this name already exists."}
```

`detail` is one sentence written for a person and MAY be shown as-is. **Do not parse it** — the
wording is not part of the contract; the status code is.

422 comes from request-model validation before any handler runs and carries a list instead:

```json
{"detail": [{"type": "string_too_short", "loc": ["body", "pair_code"],
             "msg": "String should have at least 6 characters", "input": "12"}]}
```

---

## 27. HTTP status codes

| Code | When |
|---|---|
| **200** | Success, including `PUT` with `finalize=false`. |
| **206** | Partial content for an honoured `Range`. |
| **401** | Missing, unknown or revoked token. |
| **403** | Share permission denied; wrong pairing code; owner declined; revoking another device's pairing. |
| **404** | Unknown share, missing file or folder, share unavailable, or **any path that leaves the share**. |
| **409** | Name already taken; wrong resume offset; not in pairing mode; non-empty folder without `recursive`; checksum mismatch at finalize; unacceptable file name. |
| **413** | Upload exceeds the owner's size limit. |
| **416** | `Range` offset at or past the end of the file. |
| **422** | Request body failed validation. |
| **429** | Pairing rate-limited or locked out. |

Note that a rejected *path* is 404 while a rejected *name* is 409. A refused path is deliberately
indistinguishable from a missing one — it tells a prober nothing.

## 29. Filename and path rules

### Paths (`?path=`)

Share-relative, POSIX separators, no leading slash. `""` is the share root. Backslashes are
normalised to forward slashes before validation.

Refused with **404** `The path leaves the shared folder.`:

- `..` in any component
- absolute paths, under **either** POSIX or Windows rules
- UNC paths (`//server/share`)
- drive-qualified paths (`C:\...`), and any component containing `:`
- NUL bytes
- anything that, after resolving symlinks and Windows junctions, lands outside the share root

The check is two-phase: reject the obvious before touching disk, then canonicalise and **prove**
containment with `relative_to(root)`. Symlinks and junctions are caught by the second phase.

### Names (`name`, `new_name`, multipart filename)

One safe leaf on **every** platform. Refused with **409**:

- empty, whitespace-only, `.` or `..`
- containing a separator under POSIX **or** Windows rules
- containing `< > : " / \ | ? *` or any control character `0x00`–`0x1f`
- leading whitespace, or a trailing space or dot
- a Windows reserved device name — `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` —
  including with an extension (`CON.txt`)
- longer than 255 characters

A name is **rejected, never silently rewritten**. A name carrying a separator is a caller bug or an
attack, not something to salvage. A client SHOULD apply the same rules locally so the user finds out
before the transfer starts.

Note the asymmetry: Android filenames may legally contain `:`, `?` and `*`; a Windows peer will
refuse them. Sanitise before sending and tell the user what changed.

## 30. Security requirements for a client

Mandatory:

1. **Pin the certificate.** Refuse a mismatch outright; never offer an override.
2. Show the owner a fingerprint to compare, in the same 16-character grouped form.
3. Store the token encrypted at rest.
4. Send the token only in `X-LanLink-Token`, only over TLS, only to the pinned peer.
5. Never pair automatically. Discovery is not consent; **LAN membership is never authorisation**.
6. Validate names and paths locally as well (§29). Never build a local path from a remote string
   without validating it — a remote listing is untrusted input.
7. Verify SHA-256 before presenting a downloaded file as complete.
8. Never write a downloaded file under its real name until it is verified.
9. Do not log tokens, pairing codes, or full invite URLs.
10. Treat `scheme=http` as a warning state.

Forbidden:

- Embedding a WebView, browser, or HTML interface for any part of the product.
- Trusting a system CA store for these connections.
- Weakening the sandbox, the pairing rules, or the permission flags to make something convenient.

## 31. Compatibility requirements for the Android client

- **Kotlin, native UI, no WebView.**
- Discovery: `NsdManager` on `_lanlink._tcp.`, or JmDNS. Handle Android's occasionally unreliable
  TXT resolution by falling back to manual `host:port` entry and to invite scanning. Multicast may
  need a `WifiManager.MulticastLock` on some devices.
- TLS: OkHttp with a custom `X509TrustManager` holding exactly the pinned certificate. Not
  `CertificatePinner` (that pins a public-key hash against a hostname) and not Network Security
  Config (static, while the pin is learned at runtime).
- Storage: SAF (`ACTION_OPEN_DOCUMENT_TREE`) for user-chosen folders. Do not assume a real path
  exists — copy through a `ContentResolver` stream. Streaming uploads (§12a) work directly from an
  `InputStream`, which is the reason to prefer them.
- Resume across process death: persist `share_id`, `path`, `name` and the offset; re-query §12c on
  restart rather than trusting a remembered offset.
- Sharing the phone's own folders back is optional. A device that only consumes never needs to run
  the server side — but if it does, it MUST implement §29 exactly, and MUST NOT expose external
  storage wholesale.
- Foreground service with a notification for transfers; Android will otherwise kill them.
- `usesCleartextTraffic` stays **false**. `scheme=http` peers are a troubleshooting mode a phone
  need not support at all.

## 32. Compatibility requirements for future clients

- Treat unknown JSON members as normal. Do not fail on them and do not echo them back.
- Do not depend on `detail` wording, on field ordering, or on the `Content-Type` guessed for a
  download.
- Do not depend on `share_` id formatting beyond it being an opaque stable string.
- New endpoints appear under `/v1`; a 404 on an endpoint you expected means an older peer, and the
  client should fall back rather than report a fault.

## 33. Ecosystem & Remote Extensions

### 33a. Clipboard Synchronisation — `GET /v1/clipboard` and `POST /v1/clipboard`

Bi-directional real-time clipboard exchange between paired nodes.

* `GET /v1/clipboard` returns `{"text": "<string>"}`
* `POST /v1/clipboard` sends `{"text": "<string>"}`

### 33b. Remote Input & Media Control — `POST /v1/remote/mouse`, `POST /v1/remote/keyboard`, `POST /v1/remote/media`

* `POST /v1/remote/mouse` accepts touch/pointer coordinates and actions (`move`, `abs_move`, `click`, `rclick`, `scroll`).
* `POST /v1/remote/keyboard` accepts key names (`enter`, `backspace`, `tab`, `escape`, `space`, `arrows`, `ctrl_c`, etc.) or text payloads (`action="text"`, `text="hello"`).
* `POST /v1/remote/media` accepts media control actions (`play_pause`, `volume_up`, `volume_down`, `mute`, `next`, `prev`).

### 33c. Screen Mirroring — `GET /v1/screen/frame`

Captures native desktop display frames compressed as JPEG for real-time remote mirroring.

* `GET /v1/screen/frame?quality=55&width=1280` returns raw JPEG image bytes.

### 33d. Automated Camera & Media Backup — `POST /v1/backup/camera`

Accepts camera photos and videos streamed directly from paired mobile devices.

* `POST /v1/backup/camera` with binary image/video body and headers `x-file-name` and `x-modified-at`.
